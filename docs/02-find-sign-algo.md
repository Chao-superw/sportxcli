# 02 · 定位并复现签名/加密算法

拿到解包后的前端源码后,要搞清楚的是每个请求怎么被签名或加密的,好让自己的请求也能通过服务端校验。这里讲方法,不含任何具体系统的密钥值。

## 1. 从请求特征反推

先抓一次真实请求(mitmproxy 或浏览器 DevTools),观察 URL 或 body 里的可疑字段。常见的有:

- 一个 `sign=<32位hex>`,大概率是 MD5。
- 一个随请求变化的 `t`(时间戳)、`r`(随机数)。

有了"输入疑似是某几个参数、输出是 32 位 hex"这个假设,就能去源码里搜。

## 2. 在源码里搜签名函数

```bash
grep -rInE "md5|MD5|sign|Sign|CryptoJS" <解包目录>
```

典型的 `SignMD5` 是这个套路:把参数按 key 排序,拼成 `k1=v1&k2=v2...`,追加一个固定盐,再取 MD5。把这段 JS 抽出来,用 Python 复刻一份,拿真实抓包的输入喂进去,比对输出。对上了就说明复现成功。

## 3. 如果 body 是密文

有些接口 body 是 AES 密文。在源码里搜 `CryptoJS.AES` / `mode` / `iv`,通常能找到:

- 模式(常见 `AES-128-CBC`)
- key 与 iv(可能硬编码,也可能由某函数派生)

同样用 Python(`pycryptodome`)复刻加解密,用抓包样本验证往返一致。

## 4. 产物

复现成功后,你会得到一个"给定参数,算出正确 sign 或密文"的本地实现。注意,key、iv、盐都是目标系统的机密,只应保存在你本地的 `config.toml`,绝不要提交进仓库。

下一步:即便签名对了,请求仍可能被动态 WAF 拦。见 [03-anti-bot-bypass.md](03-anti-bot-bypass.md)。
